## 3. 命令表（**本节已按第二轮实测重写，第一版结论有错**）

> ⚠️ **自我更正**：我第一轮只扫 `mov dword [buf], imm32` 且首字节恰为 `0xA1` 的模式，
> 得出"仅 3 条命令、无 0xA0 大报告、无 1024B blob"的结论——**那是错的**。
> 漏掉的原因：命令码不一定写在 64 字节小报告的 buf[0]，还可以走 **1041 字节大报告**路径，
> 而大报告头 `0x8A0` 的首字节是 `0xA0` 而非 `0xA1`，被我的过滤条件直接排除。
>
> 第二轮改用可靠方法：**先定位全部 `HidD_*` 调用点 → 回溯所在函数 → 读完整反汇编**，
> 找到 4 个成对的高层协议函数，命令表与 blob 机制才完整浮现。

### 传输层（4 个小函数，0x40F4A0–0x40F980 区）

| RVA | 作用 |
|---|---|
| `0x40F730` | 开设备（`CreateFile` + `HIDD_ATTRIBUTES`） |
| `0x40F7E0` | **发送** `HidD_SetFeature`，含错误码重试 |
| `0x40F8A0` | **读取** `HidD_GetFeature` |
| `0x40F96A` | 查询（未被调用） |

### 高层协议函数（4 个，每个都成对 Send+Recv）

| 函数 RVA | 报告头 dword | 线上字节（buf[0] 起） | 长度 | 作用 |
|---|---|---|---|---|
| `0x40FA30` | `0x3A1` | **`A1 03 00 00`** | 64 B | 读 1 字节（回复取 buf[16]） |
| `0x40FAE0` | `0x4A1` | **`A1 04 00 00`** | 64 B | 写：`buf[4]=0, buf[5]=入参` |
| `0x40FC80` | `0x7A1` | **`A1 07 00 00`** | 64 B | 写整块配置，随后 `Sleep(80)` |
| **`0x40FB90`** | **`0x8A0`** | **`A0 08 00 00`** | **1041 B** | **★ 1024B 配置 blob 读写** |

### ★ `0x40FB90` —— 1024B blob 大报告（关键发现）

```
push 0x400                        ; blob = 1024 字节
lea eax, [ebp-0x858] / push 0 / push eax
call memset                       ; 清零 blob
lea eax, [ebp-0x858] / mov ecx, esi
call 0x40FD60                     ; ← 字段重排函数，见下
push 0x411                        ; 1041 = 16 头部 + 1024 blob + report id
lea ecx, [ebp-0x458] / push 0 / push ecx
call memset                       ; 清零大报告
mov dl, byte ptr [ebp+8]          ; 入参（子命令）
mov dword [ebp-0x458], 0x8A0     ; ★ 报告头 → A0 08 00 00
mov byte  [ebp-0x454], bl        ; buf[4] = 0
mov byte  [ebp-0x453], dl        ; buf[5] = 子命令
mov word  [ebp-0x452], bx        ; buf[6..7] = 0
mov ecx, 0x100                    ; ★ 256 dword
lea esi, [ebp-0x858]             ;   源 = blob
lea edi, [ebp-0x448]             ;   目的 = 报告基址 +16  ★
rep movsd                         ; 拷贝 1024 B
mov esi, 0x411 / mov edi, [ebp-0x458]
call 0x40F7E0                     ; HidD_SetFeature(len=1041)
push 0x50 / call Sleep           ; Sleep(80ms)
cmp esi, ebx / jne → 成功分支
--- 成功后再读一次 64B 状态 ---
push 0x40 / memset / mov byte [buf], 0xA1 / call 0x40F8A0
cmp eax, ebx / sete al / inc al  ; 返回 1(成功) / 2(失败)
```

### `0x40FD60` —— blob 内部字段重排

298 条 `movzx reg, [ecx+N] / mov [eax+M], reg` 逐字段搬运，说明**官方内部 blob 布局
与线上布局不一致**，发送前要重排。已提取 268 组映射（留证 `re/upstream/o_fd60.txt`），
但目标偏移有重复（`mov reg, reg` 等形式未被正则完整捕获），
**完整映射表尚未逐字节核实，暂不作为结论使用**。

## 4. 与 4k 族的对照 —— ★ 实测后结论改写

### 配置通道：逐字节同构

| 项 | XM1（2020）实测 | 4k 无线族 |
|---|---|---|
| 大报告 | **`0xA0`，1041 B** | `0xA0`，1041 B |
| blob 长度 | **1024 B** | 1024 B |
| blob 位置 | 报告**偏移 16** | 偏移 16 |
| 小报告 | `0xA1`，64 B | `0xA1`，64 B |
| 命令码位置 | `buf[1]` | `buf[1]` |
| 写后延时 | `Sleep(80)` | 官方 4k 工具 100–880ms |
| `HidD_SetFeature` 重试 | `{0x15,0x17,0x1D,0x57,0x65B}` ×4 / 50ms | **完全相同** |

**XM1 与 4k 无线族是同一套协议框架**，差异只在：

| 项 | XM1 | 4k 无线族 |
|---|---|---|
| VID | `0x22D4`（2020） | `0x3367` |
| 命令条数 | **4 条**（0x03/0x04/0x07/0x08） | 13 条 |
| 状态字节 | **无**（看 `HidD` 返回码） | `[1]`/`[2]`，有 busy 重试 |
| CPI 档数 | **3 档**（工具 UI 原文） | 4 档 |
| 探测/唤醒 | 无独立唤醒命令 | `0x0F`（无线专属） |
| 配置持久化 | 另有 `.profile` / `pfList.dat` **文件** | blob 直接即配置 |

**实践意义**：现有网页版代码（`src/main.ts` 的 4k 路径）**几乎可以原样支持 XM1**，
需要改的只有：① VID/PID 与型号表 ② 命令码只取 4 条 ③ 去掉状态字节判定
④ CPI 档数改 3 ⑤ 加 blob↔内部布局的重排层。

## 5. VID/PID —— ★ 已从真机确认（2026-10-08）

用户在 Windows 上插入 XM1 后枚举得到，静态逆向拿不到的那块拼图补上了：

| 项 | 实测值 |
|---|---|
| **VID : PID** | **`0x22D4` : `0x1803`** |
| **REV（固件）** | **`0x0229`** = 固件 **2.29** ✓（README 要求软件 1.09 只配 2.29） |
| 设备类 | Composite Device，`usbccgp` / `HidUsb` |
| 复合结构 | MI_00 = 鼠标指针（`mouhid`，SubClass 01 Prot 02）；MI_01 = 厂商配置集合 |

**有趣的巧合**：第一轮我在 UTF-16 键名区找到的 `22D4` / `1803`（当时判定为 INI 键名、
"不是硬编码 VID/PID"）——**正是真实的 VID/PID**。厂商把同一组数字同时当作配置键名使用。

### 接口集合全图（MI_01 下 5 个集合）

| 集合 | Usage Page / Usage | 说明 |
|---|---|---|
| MI_00 Col00 | `0001/0002` | 标准鼠标指针 |
| **MI_01 Col01** | **`FF01/0002`** | **★ 配置通道（与 4k 无线族同接口页）** |
| MI_01 Col02 | `FF01/…` | 厂商定义（`HID_DEVICE_UP:FF01_U:0002` 记在 Col02） |
| MI_01 Col03 | `000C/0001` | 消费者控制（`hidserv.inf`） |
| MI_01 Col04 | `FF02/0001` | 厂商定义 |
| MI_01 Col05 | `FF02/0002` | 厂商定义 ← **与 XM2we 同接口页** |

**关键结论**：XM1 的配置接口是 **`0xFF01` / `0x0002`**，与 4k 族完全相同——
所以网页版的过滤器链只需再加一条 `{vendorId: 0x22D4, usagePage: 0xFF01, usage: 0x02}`。

⚠️ XM1 同时暴露了 `FF02:0001` 与 `FF02:0002` 两个集合（后者与 XM2we 的接口页相同），
**别误选**——从官方 v1.09 的枚举方式（纯 GUID 匹配，不筛 usage page）看，
工具是打开后按 report 描述符/长度区分的。网页版用 `FF01:02` 精确匹配即可避开歧义。

### `22D4` 世代的归属（修正旧结论）

第一轮我写"XM1 的 VID/PID 不硬编码，只能靠真机"，并推测 `22D4` 只是键名——**推测对了一半**：
枚举确实不筛 PID（实测调用点附近无任何 PID 常量），但 `22D4`/`1803` 就是真实的 VID/PID。
`0x22D4` 也是初代 OP1w 4k 的 VID，所以 XM1 属 **22D4 世代**。

## 6.5 ★★★ 2026-10-09 事故记录：XM1 写入路径永久停用

**用户报告**："你网页驱动写的不行有 bug，读取或者重置了鼠标，鼠标 dpi 等信息丢失了"，
需用官方驱动重新设置 DPI。**即：我的工具不是读取失败，而是把鼠标配置清零了。**

### 肇事的代码

`readBlobXm1()` 构造了一个 1041 字节的 `0xA0` 大报告：
头部 8 字节正确，**1024 字节负载全零**，然后直接 `sendFeatureReport`。
**这个报文的形态本身就是一次配置写入。**

### 三个叠加的设计错误

1. **把 `buf[1]=0x08` 当成"读命令"** —— 反汇编里它其实是**子命令**，
   读/写语义由固件解释，未确认前不该猜。
2. **明知 blob 重排层（`0x40FD60`，298 条搬运）未逐字节核实，仍然发了完整 blob 报文。**
   UI 上标注"只读"不等于安全——设备根本不知道我只想读。
3. **官方流程是「读回 1024B → 改动 → 重排 → 写回」**，
   我跳过了第一步直接发空 blob，等价于 **读取 = 清空**。

### 现在的处理：三重封锁，任何一层都足以挡住

| 层 | 位置 | 作用 |
|---|---|---|
| 1 | `readBlobXm1()` → `xm1Unsupported()` | 直接抛错，不存在 blob 发送 |
| 2 | `transact()` 开头 `if (xm1) xm1Unsupported()` | 挡住 4k 族全部 13 条命令 |
| 3 | `openDevice()` 替换 `d.sendFeatureReport` 为抛错桩 | **运行时兜底**：未来新增任何调用点也无法触达硬件 |

审计结果：`sendFeatureReport(RPT_BULK, ...)` 调用点已归零，
仅剩的两处是 4k 命令通道（有守卫）与 XM2we（独立模块）。

UI 现在明确提示：XM1 仅识别型号，**不做任何读取或写入**，配置请用官方 v1.09 软件。

### 教训（比技术结论更重要）

> **"只读"是一个 UI 概念，不是协议保证。**
> 只要报文里带着完整的负载缓冲区，它在设备侧就是一次写。
> 在协议语义未确认之前，**唯一安全的做法是不发**——
> 标个警告然后照发，是把风险转嫁给了用户的硬件。

## 6.6 ★ 真机 blob 结构分析（2026-10-09 首份实测数据）

读通路打通后取得第一份完整 **1024 字节** blob（真机导出，留存 `re/xm1_blob_2026-10-09.bin`）。

### 概览

- 仅 **61 个非零字节**，集中在 `0x012–0x0E5`
- `0x090–0x0BF`、`0x0E8–0x3FF` 全零
- ⚠️ 注意这是**内部布局**（读路径 `0x40FC80` 末尾 `call 0x4103D0` 重排的结果），
  与写路径下发的**线上布局**（`0x40FD60`）**偏移不同**，两者不可混用

### 已识别结构 A：0x06B 起，步长 7，6 项

| # | 偏移 | 数据 |
|---|---|---|
| 0 | 0x06B | `0f 00 02 00 00 00 00` |
| 1 | 0x072 | `0f 00 04 00 00 00 00` |
| 2 | 0x079 | `0f 00 10 00 00 00 00` |
| 3 | 0x080 | `0f 00 08 00 00 00 00` |
| 4 | 0x087 | `0f 09 f1 00 00 00 00` |
| 5 | 0x08E | `0f 00 00 00 00 00 00` |

每项以 `0x0F` 开头，第 3 字节是取值：**2 / 4 / 16 / 8**。
~~推测为 4 档回报率枚举~~ → **已被 6.8 节的差分推翻**：回报率改档后此表零变化，
故此表**不是**回报率（回看该 6 项与 Light 页面的 6 个控件数吻合，
是「3 个 LED 区 × (LED + COLOR)」的候选，待 6.9 节的灯效差分验证）。第 5 项 `09 f1` 待查。

### 已识别结构 B：0x0C7 起，步长 5，7 项

| # | 偏移 | 数据 |
|---|---|---|
| 0–6 | 0x0C7 + 5n | `0d 00 00 00 00`（7 项全部相同） |

7 项 × 5 字节，每项首字节 `0x0D`。**推测为 7 个按键的映射表**
（XM1 共 7 键：左/右/中/侧1/侧2/DPI+/DPI−）。全为 `0x0D` 说明当前是默认映射。

### CPI 候选值（成对出现）

| 值 | X 位置 | Y 位置 |
|---|---|---|
| 400 | `0x034` | `0x036` |
| 800 | `0x03D` | `0x03F` |
| 1600 | `0x052` | `0x054` |
| 3200 | `0x05C` | `0x05E` |

每个值**出现两次且相邻**（间隔 2 字节）→ **X/Y 分开存储**，印证 XY 独立 CPI。
4 个值 ×2 = 8 个 u16，共 16 字节，与前段非零区段吻合。

**但各档起点间隔不均（9 / 21 / 10 字节）**，说明档位结构可能变长（含 LED/标志字段），
或 400/800/1600/3200 并非同一张表的连续 4 项。**需差分数据才能定案。**

### ★★ 差分结果（2026-10-09）：CPI 结构已确凿

操作：官方软件把一档 CPI 从 **800 改成 1150**，其余不动。
差分显示**仅 4 个字节变化**：

| 偏移 | 旧 | 新 | 解读 |
|---|---|---|---|
| `0x03D-0x03E` | `20 03` = 800 | `7e 04` = 1150 | **CPI X**（u16 小端，直接存储） |
| `0x03F-0x040` | `20 03` = 800 | `7e 04` = 1150 | **CPI Y** |

**结论：CPI 每档 = `[X:u16][Y:u16]`，小端、无缩放**（1150 = 0x047E 直存）。

### CPI 四组位置（内部布局）

| 组 | X 偏移 | Y 偏移 | 基准值 |
|---|---|---|---|
| 0 | `0x034` | `0x036` | 400 |
| 1 | `0x03D` | `0x03F` | 800 → 1150 |
| 2 | `0x052` | `0x054` | 1600 |
| 3 | `0x05C` | `0x05E` | 3200 |

⚠️ **待澄清**：用户表述为"改档 1（400）"，但变化的是 **800 那一组**。
说明官方软件的档位编号与 blob 顺序不一致，或第 0 组不是普通档位。
**组间间距不规律（9 / 21 / 10 字节）**，中间可能夹有其他字段（LED/标志）。
→ 需再改一档验证组 2/3 的独立性与顺序。

### 下一步：差分法（唯一可靠手段）

1. 官方软件改**一个**已知值（如 CPI 档 1：400 → 1234）
2. 保存
3. 网页重新读取 → 导出
4. 对比两份 blob，**变化的字节即该字段的确切偏移**

分析脚本：`re/xm1_blob_struct.py`（结构发现）、`re/xm1_blob_analysis.py`（首轮启发式）。

然后把导出的 blob 逐字节比对。**变化的字节即字段偏移。**

- 档位间距不均（9 / 21 / 10），说明档位数据在内部布局中不是连续块，

## 6.8 ★ 第四次差分：实体按键改回报率 → blob **零变化**（2026-10-09）

**操作**：用鼠标**实体按键**改回报率（用户说明：回报率**只能**用实体键改，改完灯效随之变化）。

### 结论（重要）

1. **回报率不在 1024B 配置 blob 里**。改档不落盘到该 blob，

## 6.9 ★★ 单字节命令通道：blob 之外的第二套配置存储

既然回报率不在 blob 里，就去找它存在哪。反汇编官方两处调用链
（脚本 `re/upstream/xm1_single_byte.py`，可复现）：

```
读取事务（函数 0x418F80）
  call 0x40FA30   cmd 0x03  读 1 字节（返回码须 = 1）
  call 0x40FC80   cmd 0x07  读 1024B blob
  call 0x40E550   解析 blob → 配置对象

应用事务（函数 0x41A070）
  call 0x40F530   打开设备（两个 u16 全局量作参数，疑似 VID/PID 运行时读入）
  call 0x40FA30   cmd 0x03  读 1 字节（返回码须 = 1）
  call 0x40E0D0   把配置对象打包成 blob
  call 0x40FB90   cmd 0x08  写 1024B blob
  call 0x40FAE0   cmd 0x04  写回**同一个字节**，值取自 [[esi+0xC88]+4]
```

### 报文形态（与 blob 读同形，均无负载）

| 命令 | 函数 | 线上字节 | 长度 | 方向 |
|---|---|---|---|---|
| `0x03` | 0x40FA30 | `A1 03 00 00` + 全零 | 64B | 读（结果写回传入的 1 字节缓冲，函数返回码 1=成功） |
| `0x04` | 0x40FAE0 | `A1 04 00 00 00 <value> 00 00` | 64B | **写 1 字节**（值在 buf[5]）；失败返回 2；成功后 Sleep(1500ms) |
| `0x07` | 0x40FC80 | `A1 07 00 00` + 全零 | 64B 请求 + **1041B** GetFeature 读回 | 读 blob |
| `0x08` | 0x40FB90 | `A0 08 00 00` + 1024B 负载 | 1041B | 写 blob（**停用**） |

**关键推论**：单字节与 blob 是**两套独立存储**，官方读时同读、写时同写。
这正好解释了 6.8 节的零变化 —— 回报率（及可能的"激活档"之类全局量）
落在那条单字节通道上，而不是 blob。

### 本工具的处理

- **只读** cmd `0x03`（`xm1QueryByte()`）：63 字节、除命令码外全零，
  与 blob 读同级安全，已加入发送白名单。
- **写** cmd `0x04` **不在白名单内**：单字节语义未确认，盲写同样是改配置。
- 白名单现在是 `{0x03, 0x07}` 两条无负载查询；任何带负载报文（尤其 1041B）一律拦截。

### ⚠️ 方法论教训（这轮最重要的一条）

第一轮"命令表仅 3 条"的错误根源：**过滤条件只认首字节 `0xA1`**，
而 XM1 的大报告头是 `0x8A0`（首字节 `0xA0`）——于是整条 blob 路径被静默排除。

**正确做法**（第二轮才用上）：
1. 先用 `FF 15 <IAT>` 找出**所有** `HidD_*` 调用点
2. 对每个调用点**回溯到函数起点**，导出完整反汇编
3. 用传输层函数（`SetFeature`/`GetFeature` 封装）作为锚点，**反查它们的调用者**
4. 人工判读命令码与缓冲区布局

**不要用"立即数取值范围"当过滤器**——它会把非常规路径（不同报告 ID、不同长度）
悄悄滤掉，而且**不报错**。

### ⚠️ x86 调用点扫描的两个坑

- 间接调用是 `FF 15 <IAT 绝对地址>`（x86 无 `call reg` 相对形式）
- **IAT 地址 = RVA + ImageBase**。我两次都栽在这：第一次当 RVA 搜、
  第二次漏了 ImageBase，两次都扫出 **0 命中却不报错**，差点得出"没导入"的错误结论。
