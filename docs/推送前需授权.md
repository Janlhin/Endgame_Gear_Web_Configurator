# 推送前需要你做的一件事：给Git 令牌加 workflow 权限

## 为什么需要

推送被 GitHub 拒绝了，原话是：

```text
! [remote rejected] main -> main (refusing to allow an OAuth App to create
  or update workflow `.github/workflows/deploy.yml` without `workflow` scope)
```

意思是：**当前令牌的权限不够**，无法上传 `.github/workflows/` 里的文件。
本项目的 `verify.yml`（CI 校验）与 `deploy.yml`（Pages 发布）都在这个目录里，
所以 GitHub 直接拒绝了整个推送。

这不是代码问题，也不是网络问题。远端仓库存在且可访问，只是令牌少一个权限。

## ★ 根因诊断：为什么 `gh auth refresh` 解决不了本项目（2026-10-09 实测）

用户执行了 `gh auth refresh -s workflow` 并在浏览器授权，但 `git push` 仍以
**完全相同的理由**被拒。查下来发现根因是**凭据分属两套，互不相通**。

**`git:https://Janlhin@github.com`** — `git push` 实际用的就是这条。
`gho_` 开头、40 字符、实测**有效**（`/user` 返回 Janlhin），但 scope 缺 `workflow`。

**`gh:github.com:Janlhin`** — `gh` CLI 自己用（keyring）。
`gh auth refresh` 刷的是**这条**，与上面那条无关。

**结论**：`gh auth refresh` 加的权限**不会**流到 `git push` 使用的令牌上。
它俩是两套独立的凭据存储。所以「完成 `gh auth refresh` 后重试」这条路**走不通**——
无论怎么刷新 `gh`，`git push` 用的仍是那条缺 `workflow` 的 `gho_` 令牌。

顺带修正两处环境事实：

- 本机有**两个 gh**：`C:\Program Files\GitHub CLI\gh.exe`（2.102.0，winget）
  与 `C:\Users\Janlhin\.workbuddy\binaries\gh\bin\gh.exe`（2.88.1，PortableGit 自带）。
  全局 `credential.https://github.com.helper` 指向的是**后者**。
  PATH 里两个都查不到（`where gh` 报「无法找到文件」）。
- `git config credential.helper` = `helper-selector` + `git-credential-wincred.exe`。

## 解除方式（三选一，推荐 A）

### 路线 A（推荐）：删掉旧的 `git:` 凭据，让 git 回落到 `gh` 的令牌

`gh` 的令牌经 `gh auth refresh -s workflow` 已（或即将）具备 `workflow` 权限。
把 `git:` 那条旧凭据移除后，git 会向下询问 helper，最终由
`gh auth git-credential` 供出**已授权的**令牌。

```powershell
# 1. 确认 gh 侧 scope 已含 workflow
& "C:\Program Files\GitHub CLI\gh.exe" api -X GET user -i 2>&1 | Select-String "^X-Oauth-Scopes"

# 2. 删除 wincred 里那条旧的 git 凭据（注意：只删 git: 那条，保留 gh: 那条）
& cmdkey /delete:git:https://Janlhin@github.com

# 3. 回项目目录重试推送
```

> 第 2 步是**不可逆**的凭据删除，但它只是删掉一个已证明缺权限的旧令牌；
> 若 git 随后无法认证，重新授权即可恢复，不影响仓库内容。

### 路线 B：把带 `workflow` 的令牌直接写进 remote URL

```powershell
& "C:\Program Files\GitHub CLI\gh.exe" auth token
# 复制输出的令牌，然后：
git remote set-url origin https://Janlhin:<令牌>@github.com/Janlhin/Endgame_Gear_Web_Configurator.git
git push -u origin main
# 推完务必换回干净地址，令牌会留在 .git/config 里：
git remote set-url origin https://github.com/Janlhin/Endgame_Gear_Web_Configurator.git
```

### 路线 C：新建带 `workflow` 的 PAT 并让 wincred 记住它

新建 PAT（勾 `workflow`）后，删掉旧 `git:` 凭据（路线 A 第 2 步），
下一次 `git push` 会弹出浏览器/凭据窗口，用新 PAT 登录即可。

### 前置：确认 `gh` 侧令牌已具备 `workflow`

无论走哪条路线，都建议先确认 `gh` 自己的令牌已加上权限
（路线 A 依赖这一点；`gh` 有两个副本，用完整路径避免 PATH 找不到）：

```powershell
& "C:\Program Files\GitHub CLI\gh.exe" auth refresh -s workflow
& "C:\Program Files\GitHub CLI\gh.exe" api -X GET user -i 2>&1 |
  Select-String "^X-Oauth-Scopes"
# 期望：X-Oauth-Scopes: gist, read:org, repo, workflow
```

若这一步仍拿不到 `workflow`，改走路线 C（新建 PAT）更直接。

`deploy.yml` 对 `push: main` 会**自动触发 Pages 发布**——也就是这一步等于上线。
你之前已知悉并接受，这里再确认一次，避免意外。

## 我被否决的替代方案

有人会想「把 workflow 文件排除掉，先把代码推上去」——我试这条路是错的：

- CI 与 Pages 部署会**完全失效**，且失效状态不会立刻暴露
- 本地工作树要临时缺两个文件，等于制造一个不一致的状态
- 用更大的问题换小问题，不划算

所以正确路径就是补权限。
