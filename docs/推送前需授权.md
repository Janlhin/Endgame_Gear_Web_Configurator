# 推送前需要你做的一件事：给 Git 令牌授权

## 为什么需要

推送被 GitHub 拒绝了，**先后两种不同的报错**（都指向令牌权限，不是代码问题）：

```text
① [remote rejected] main -> main (refusing to allow an OAuth App to create
  or update workflow `.github/workflows/deploy.yml` without `workflow` scope)

② remote: Permission to Janlhin/Endgame_Gear_Web_Configurator.git denied to Janlhin.
   fatal: unable to access '...': The requested URL returned error: 403
```

本项目的 `verify.yml`（CI 校验）与 `deploy.yml`（Pages 发布）都在 `.github/workflows/` 里，
推送该目录需要令牌对 **workflows** 有写权限。远端仓库存在且可访问，只是令牌权限不够。

---

## ★ 根因诊断：为什么 `gh auth refresh` 解决不了（2026-10-09 实测）

用户执行 `gh auth refresh -s workflow` 并在浏览器授权，重推仍是**逐字相同**的 ①。
查下来是**凭据分属两套、互不相通**：

**`git:https://Janlhin@github.com`** — `git push` 实际用的就是这条。
`gho_` 开头、40 字符、实测**有效**（`/user` 返回 Janlhin），但缺 `workflow`。

**`gh:github.com:Janlhin`** — `gh` CLI 自己用（keyring）。
`gh auth refresh` 刷的是**这条**，与上面那条无关。

`git config credential.helper` = `helper-selector` + `git-credential-wincred.exe`，
所以 push 走 wincred，**永远取不到 gh 那条已刷新的令牌**。

**结论**：无论怎么 `gh auth refresh`，`git push` 用的仍是那条缺 `workflow` 的令牌。
——「授权做了却没用上」的典型陷阱：查`gh auth status` 会显示一切正常，
从而掩盖「消费者根本没用这份凭据」的事实。

---

## ★ 第二次尝试：fine-grained PAT 仍被拒（403）——2026-10-09 实测

改用新建的 **fine-grained PAT**（`github_pat_` 前缀）。实测结果：

- `/user` 验证**有效、身份正确**
- `GET /repos/<repo>` 返回 `permissions: {admin: true, maintain: true, push: true, ...}`
- 但 `git push` **仍被拒**：`Permission to <repo>.git denied to <user>`（403）

**含义**：该令牌有仓库内容权限（push/admin），但**缺少 `Workflows` 权限项**。
`permissions` 字段涵盖仓库读写，**workflows 是独立权限项**、不体现在该字段——
这正是「明明有 push 权限却推不上去」的原因。

### ⚠️ 本文件此前的一处错误结论（已更正）

先前写「仓库当前是**私密的**」——**不成立**。实测：

```text
GET https://github.com/Janlhin/...            → HTTP 200
GET https://api.github.com/repos/Janlhin/...  → HTTP 403 + "API rate limit exceeded"
```

对照：已知公开仓库 `microsoft/vscode` 的 API 查询**同样 403**。故那是**速率限制**，
不是仓库私密。带认证重查得`private: false` —— **仓库确实是公开的**。

**教训**：`curl` 无返回 / 403 有多种成因（速率限制、私密、网络），
**必须用对照仓库 + 读响应体来区分**。把「一个渠道失败」直接写成事实结论，
与判例十五同源。

### 两类令牌报错形态对比（最快的判别依据）

| 令牌类型 | 权限表达 | 典型报错 |
| --- | --- | --- |
| OAuth App 令牌（`gho_`） | OAuth **scope**，`X-OAuth-Scopes` 头**可见** | `... without workflow scope` —— **明确指出缺哪个 scope** |
| fine-grained PAT（`github_pat_`） | 绑定到仓库与**具体权限项**，API **不返回** scope 头 | `Permission to <repo>.git denied to <user>` —— **不提示缺什么** |

### 补充：无权限端点返回 404 而非 403

实测 `GET /repos/<repo>/contents` 与 `/workflows` **均返回 404**（非 403）——
GitHub 对无权限资源故意隐藏存在性。**故不能靠「哪个端点 403」反推缺哪个权限**，
排查必须以令牌配置页为准。

## 一次性推送的安全做法（已实践）

不把令牌写进 remote URL、也不落盘 `.git/config`：

1. 令牌写入临时文件（`chmod 600`）
2. 写 askpass 脚本，按提示语返回用户名 / 密码
3. `GIT_ASKPASS=<脚本> GIT_TERMINAL_PROMPT=0 git -c credential.helper= push`
4. **推完立刻删除**两个临时文件

已核验：`remote -v` 与 `.git/config` **均无令牌残留**，临时文件已删除。

## ★ 第四次尝试：PAT 401 无效，但 `gh` 链路已通（2026-10-09 实测）

用户提供了一个新 fine-grained PAT，**API 返回 401 未经授权**（长度 93、前缀正确）。
401 与 403 含义不同：**401 = 令牌本身无效**（已撤销/过期/复制有误），
403 = 有效但无权。**先分清这两者，可避免把「令牌坏了」误判成「权限不够」。**

与此同时发现**局面已发生实质变化**——此前删掉的 `git:` 凭据现在有了替代者：

| 环节 | 状态 |
|---|---|
| `git:https://Janlhin@github.com`（wincred） | **已删除**（上一轮按方案执行） |
| `gh auth git-credential`（全局 helper） | **可用**——实测 `gh auth git-credential get` 正常返回用户名 + 令牌 |
| gh 侧令牌 scope | `gist, read:org, repo` —— **只缺 `workflow`** |

实测推送报错**回到最初那句** `... without workflow scope`，
说明 git 现在取用的**正是 gh 那条令牌**。链路已通，**只差一个 scope**。

### 结论：不必再用 PAT，`gh auth refresh` 即可收尾

```powershell
& "C:\Program Files\GitHub CLI\gh.exe" auth refresh -h github.com -s workflow
& "C:\Program Files\GitHub CLI\gh.exe" api -X GET user -i 2>&1 | Select-String "^X-Oauth-Scopes"
# 期望：gist, read:org, repo, workflow
```

补上后推送即可成功，**且后续无需再向任何人传递令牌**。

⚠️ 顺带更正一处此前记错的路径：全局
`credential.https://github.com.helper` 实际指向
**`C:\Program Files\GitHub CLI\gh.exe`**（2.102.0），
**不是**先前记录的 PortableGit 那份（2.88.1）。

## 解除方式（三选一，推荐 A）

### 路线 A（推荐）：给 `gh` 补 `workflow` scope——链路已通，只差这一项

实测已确认：`git push` 现在经 `gh auth git-credential` 取用令牌
（wincred 旧条目已删），**唯一缺口是 gh 侧缺 `workflow`**。

```powershell
& "C:\Program Files\GitHub CLI\gh.exe" auth refresh -h github.com -s workflow
& "C:\Program Files\GitHub CLI\gh.exe" api -X GET user -i 2>&1 | Select-String "^X-Oauth-Scopes"
# 期望：gist, read:org, repo, workflow
```

补上后即可推送，**且后续无需再传递任何令牌**。

### 路线 B：fine-grained PAT（当前手上这枚 401 无效，需重建）

编辑 <https://github.com/settings/personal-access-tokens> 的令牌：

- **Repository access**：确认已选中 `Endgame_Gear_Web_Configurator`
- **Repository permissions**：`Contents` → Read and write，
  **`Workflows` → Read and write** ← 后者是关键，**默认 No access，不随 Contents 附带**

### 路线 C：改用 classic PAT（权限可自行验证）

<https://github.com/settings/tokens/new>，勾选 `repo` + `workflow`。
生成后先自证 scope 再让我推送：

```bash
curl -sI -H "Authorization: Bearer <令牌>" https://api.github.com/user | grep -i x-oauth-scopes
```

## 推完之后会发生什么

`deploy.yml` 对 `push: main` 会**自动触发 Pages 发布**——也就是这一步等于上线。
你之前已知悉并接受，这里再确认一次，避免意外。

推成功后会启动两个 CI job：

| job | 跑在哪 | 做什么 |
|---|---|---|
| `verify` | ubuntu | `npm ci` → `verify:ci`（tsc、markdownlint、217 项断言、i18n 审计、构建）+ 产物绝对路径检查 + 提交信息格式检查 |
| `ui` | windows-latest | 无头 Edge 的 8 类布局 + 22 个语言检测用例 + 复位演练 |

**这是 CI 的首次真实运行**，本地全绿不能替代它的结论。两处此前未能验证的差异会在此暴露：

- 本地 `check:ui` 跑 Python 3.13.14，CI 声明 3.12
- runner 上的无头 Edge 会被自动更新，与本地版本不一定一致

## 我被否决的替代方案

**「把 workflow 文件排除掉，先把代码推上去」**——我试这条路是错的：

- CI 与 Pages 部署会**完全失效**，且失效状态不会立刻暴露
- 本地工作树要临时缺两个文件，等于制造一个不一致的状态
- 用更大的问题换小问题，不划算

所以正确路径就是补权限，且必须补在**git 实际使用的那一份凭据**上。
