# 推送前需要你做的一件事：给 Git 令牌授权

## 为什么需要

推送被 GitHub 拒绝了，**先后两种不同的报错**（都指向令牌权限，不是代码问题）：

```text
① [remote rejected] main -> main (refusing to allow an OAuth App to create
  or update workflow `.github/workflows/deploy.yml` without `workflow` scope)

② remote: Permission to Janlhin/Endgame_Gear_Web_Configurator.git denied to Janlhin.
   fatal: unable to access '...': The requested URL returned error: 403
```

本项目的 `verify.yml`（CI 校验）与 `deploy.yml`（Pages 发布）都在 `.github/workflows/` 里，
推送该目录需要令牌对 **workflows** 有写权限。远端仓库存在且可访问，只是令牌权限不够。

---

## ★ 根因诊断：为什么 `gh auth refresh` 解决不了（2026-10-09 实测）

用户执行 `gh auth refresh -s workflow` 并在浏览器授权，重推仍是**逐字相同**的 ①。
查下来是**凭据分属两套、互不相通**：

**`git:https://Janlhin@github.com`** — `git push` 实际用的就是这条。
`gho_` 开头、40 字符、实测**有效**（`/user` 返回 Janlhin），但缺 `workflow`。

**`gh:github.com:Janlhin`** — `gh` CLI 自己用（keyring）。
`gh auth refresh` 刷的是**这条**，与上面那条无关。

`git config credential.helper` = `helper-selector` + `git-credential-wincred.exe`，
所以 push 走 wincred，**永远取不到 gh 那条已刷新的令牌**。

**结论**：无论怎么 `gh auth refresh`，`git push` 用的仍是那条缺 `workflow` 的令牌。
——「授权做了却没用上」的典型陷阱：查`gh auth status` 会显示一切正常，
从而掩盖「消费者根本没用这份凭据」的事实。

---

## ★ 第二次尝试：fine-grained PAT 也被拒（403）——2026-10-09 实测

改用新建的 **fine-grained PAT**（`github_pat_` 前缀）。该令牌 `/user` 验证**有效、
身份正确**，但 push 仍被拒，即报错 ②。

**两类令牌的报错形态完全不同，这是最快的判别依据**：

| 令牌类型 | 权限怎么表达 | 典型报错 |
| --- | --- | --- |
| OAuth App 令牌（`gho_`） | OAuth **scope**，`X-OAuth-Scopes` 头可见 | `... without workflow scope` —— **明确告诉你缺什么** |
| fine-grained PAT（`github_pat_`） | **绑定到具体仓库与权限**，API **不返回** scope 头（本项目实测为空） | `Permission to <repo>.git denied to <user>` —— **不提示缺什么** |

**关键**：fine-grained PAT 创建时必须勾选「Repository access」并**显式选中本仓库**，
否则一律 403。`/user` 通过只说明令牌本身有效，**不代表它有权访问这个仓库**——
这两件事必须分开验证，本次就是卡在后者。

另实测：匿名 `curl /repos/Janlhin/Endgame_Gear_Web_Configurator` **无返回**，
说明该仓库当前是**私密的**（早期记录为「公开」，可能其后被改过）。
若确实为私有，fine-grained PAT 的仓库授权是**必须项**，没有绕过方式。

## 一次性推送的安全做法（已实践）

不把令牌写进 remote URL、也不落盘 `.git/config`：

1. 令牌写入临时文件（`chmod 600`）
2. 写 askpass 脚本，按提示语返回用户名 / 密码
3. `GIT_ASKPASS=<脚本> GIT_TERMINAL_PROMPT=0 git -c credential.helper= push`
4. **推完立刻删除**两个临时文件

已核验：`remote -v` 与 `.git/config` **均无令牌残留**，临时文件已删除。

## 解除方式（三选一，推荐 A）

### 路线 A（推荐）：把 fine-grained PAT 授权到本仓库

编辑该令牌（<https://github.com/settings/personal-access-tokens> → 你的令牌 → Configure）：

- **Repository access**：选 `Only select repositories`，确认列表里**已选中**
  `Endgame_Gear_Web_Configurator`
- **Permissions → Repository permissions**：
  - `Contents` → **Read and write**（推送代码必需）
  - `Workflows` → **Read and write**（推送 `.github/workflows/` 必需）
- 保存后把令牌给我，我用上面「一次性推送」的做法执行。

### 路线 B：改用 classic PAT（权限可自行验证，不必靠推送试错）

<https://github.com/settings/tokens/new>，勾选 `repo`（私有仓库读写）与 `workflow`。

生成后先用这一步验证 scope 到位，再让我推送：

```bash
curl -sI -H "Authorization: Bearer <令牌>" https://api.github.com/user | grep -i x-oauth-scopes
# 期望含repo 与 workflow
```

### 路线 C：改用 `gh auth login`（gh 侧统一管理，后续无需再传令牌）

```powershell
& "C:\Program Files\GitHub CLI\gh.exe" auth login -h github.com
# 选 Login with a web browser；Scopes 里额外输入 workflow
```

登录成功后 git 会经 `credential.https://github.com.helper` 取用该令牌。

> 注意：`gh` 在本机有**两个副本**，且**都不在 bash 的 PATH 里**——
> `C:\Program Files\GitHub CLI\gh.exe`（2.102.0，winget）与
> `C:\Users\Janlhin\.workbuddy\binaries\gh\bin\gh.exe`（2.88.1，PortableGit 自带）。
> 全局 `credential.https://github.com.helper` 指向**后者**，故建议登录后者或直接改配置。
> `where gh` 报「无法找到文件」，属正常——不要据此认为 gh 未安装。

## 推完之后会发生什么

`deploy.yml` 对 `push: main` 会**自动触发 Pages 发布**——也就是这一步等于上线。
你之前已知悉并接受，这里再确认一次，避免意外。

推成功后会启动两个 CI job：

| job | 跑在哪 | 做什么 |
|---|---|---|
| `verify` | ubuntu | `npm ci` → `verify:ci`（tsc、markdownlint、217 项断言、i18n 审计、构建）+ 产物绝对路径检查 + 提交信息格式检查 |
| `ui` | windows-latest | 无头 Edge 的 8 类布局 + 22 个语言检测用例 + 复位演练 |

**这是 CI 的首次真实运行**，本地全绿不能替代它的结论。两处此前未能验证的差异会在此暴露：

- 本地 `check:ui` 跑 Python 3.13.14，CI 声明 3.12
- runner 上的无头 Edge 会被自动更新，与本地版本不一定一致

## 我被否决的替代方案

**「把 workflow 文件排除掉，先把代码推上去」**——我试这条路是错的：

- CI 与 Pages 部署会**完全失效**，且失效状态不会立刻暴露
- 本地工作树要临时缺两个文件，等于制造一个不一致的状态
- 用更大的问题换小问题，不划算

所以正确路径就是补权限，且必须补在**git 实际使用的那一份凭据**上。
