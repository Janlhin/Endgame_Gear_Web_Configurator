# 代码与架构审计报告（2026-10-20）

> 范围：`src/` 全部 24 个 TS 文件（约 5.4k 行）、构建脚本、文档链。
> 方法：逐文件通读 + 调用链推演 + 与 `re/` 下的真机/逆向证据对照；
> 关键结论均给出文件位置，可复核。
> 本轮同时修复了 4 个低风险明确缺陷，其余按「建议」列出，未擅自改动。

## 零、结论摘要

| 维度 | 结论 | 评级 |
|---|---|---|
| 安全设计 | 指针集合无条件拒绝；XM1 写入有可证明的字节级白名单；未验证族一律只读 | **强** |
| 原子性 | 单条报文无事务（协议本身无事务）；多命令写入靠「回读校验」兜底，本轮补上写入互斥 | **中**（协议上限） |
| 严谨性 | 类型收敛到位、错误路径清晰、边界多注释；仍有 2 处 `any` 泄漏与小重复 | **良** |
| 潜在 bug | 本轮修 4 个（1 个功能性死代码）；剩 4 个低风险项 | **良** |
| 架构 | 分层单向、无 import 环、文档密度高；`main.ts` 仍偏大，闸门有一处刻意重复 | **良** |

**总评**：这是一个防护意识明显高于平均水平的个人项目 —— 最危险的三处
（开接口、写 XM1、写未验证族）都有闸门且都有事故记录背书。主要短板不在
「有没有防护」，而在「多入口写入的时序」与少量「注释与实现漂移」。

## 一、原子性（写入事务）

### A-1 多命令写入没有回滚（已知上限，非缺陷）✅ 可接受

- `session.ts` 的 `applySensor()` 是 `0x14` →（可选 `0x15`）→ 回读；
  `applyPerf()` 是 `0x15` →（可选 `0x14`）→ 回读；导入是 `0x14 + 0x15 + 0x16×2`。
- 若第二条命令失败，设备停在「一半新、一半旧」的状态。协议层没有事务，
  这是无法根除的（`docs/release-safety-audit.md` 残余风险 1 已如实记录）。
- **现有缓解是有效的**：每次写完 `refreshAll()` 重读，`verifySensor/verifyPerf`
  逐项比对并把不一致列出来 —— 属于「检测而非修复」。
- **建议（低优先）**：失败时提示「请重新点击应用」，或自动重放一次完整序列；
  不要自动回滚（回滚同样是写入，风险不比原写入低）。

### A-2 写入缺少互斥 → 本轮已修 ✅

- 问题：`applySensor/applyPerf` 与导入共用同一设备，却没有「正在写」的标记。
  双击「应用」、或导入与应用并发时，两次写入会交错；8k 的 `store8k()` 更是
  绕过 `S.queue` 直接 `sendFeatureReport`（4k 的事务队列管不到它）。
- 修复：`state.ts` 新增 `S.writing`；`session.ts` 两个入口用
  `try/finally` 包住（8k 走同一条路径）；`main.ts` 的导入入口同样检查并置位；
  设备丢失复位时清零。冲突时提示新增的 `bBusy`（八语言）。
- 说明：**只读刷新不设限** —— 写入期间点刷新最多看到中间态，随后的校验会
  把它标出来，不会造成设备损坏。

### A-3 导入失败后的状态残留 → 本轮已修 ✅

- 问题：导入时先把 `S.blob` 换成文件里的 blob，再发写命令。若写失败，
  `S.blob` 仍指向「从未写进设备」的数据，后续 `guard4k()` 会误以为已读过配置。
- 修复：失败时回滚 `S.blob = prevBlob; parseBlob();`。

### A-4 `store8k()` 的重试不区分错误类型（低）

- `device-8k.ts:65-69`：连续 4 次重发，包括 `NotAllowedError`（设备已断开）
  这类重试无意义的错误。不会造成损坏，只是多花 ~200ms。
- **建议**：仅对 `NotAllowedError` 之外（或 message 含 timeout/busy）的错误重试。

## 二、严谨性

### R-1 闸门有一份刻意重复（可消除）

- `connect.ts` 与 `xm2we-ui.ts` 各有一份 `isSafeToOpen/openGuarded`。
  原因是 `connect.ts` 已 import `xm2we-ui.ts`（关闭/查询 WE 会话），
  反过来 import 会成环。两份实现目前语义一致（本轮同步改过）。
- **建议**：抽 `src/gate.ts`（零依赖，只依赖 i18n），两边都 import，
  环自然消失，也消除「改一处忘另一处」的风险。本轮未做，属于结构调整，
  需单独确认。

### R-2 `verifySensor()` 的 active 检查只对 gen2（待确认是否有意）

- `verify.ts:37`：`if (S.gen === 2 && w.active !== ...)`。
  若 v1 设备的激活档也可写，这里会漏报；若 v1 的激活档由硬件决定，
  应补一句注释说明，避免后来者误以为是遗漏。
- **建议**：补注释（本轮未改，避免误判协议语义）。

### R-3 8k 读写绕过事务队列（中）

- `device-8k.ts` 的 `readBlob8k/store8k` 直接用 `dev().sendFeatureReport`，
  不经过 `S.queue`。与 4k 的 `transact()` 混跑时（例如 8k 写入过程中触发
  一次 4k 路径的刷新 —— 实际不会发生，因为族互斥）风险低；
  但与「页面内其他 direct send」（XM1 模块）共享同一设备时，理论上可交错。
- **建议**：长期把 `sendFeatureReport` 统一收口到 transport 的一个队列化
  `send()`，各族都调用它；这是结构性改动，未做。

### R-4 `transact()` 忙重试耗尽不置 `lastFail`（低）

- `transport.ts`：状态 `0x03` 重试 4 次后抛 `StatusError(0x03)`，
  但只有「非 0x01/0x03」分支才 `S.lastFail = true`。
  于是下一次 `guarded()` 不会先 probe，可能继续撞忙。
- **建议**：忙耗尽时也置 `S.lastFail = true`（一行）。

### R-5 `buildFrame()` 有一段不可达分支（低）

- `xm2we.ts:62`：`b[2] = payload.length > 10 ? payload.length : b[2]`，
  但上一行循环已把 payload 截到 `EE_MAX = 10`，条件恒假。
- **建议**：删除或改成「显式拒绝超长 payload」。WE 族写入默认关闭，
  影响面为零。

### R-6 类型与注释漂移（已修）

- `connect.ts` 的 XM1 白名单注释仍写「逐字节回声」，而实现早已升级为
  「23 个已核实偏移可改、其余逐字节相等」→ 已更正。
- `main.ts` 里残留两段 isSafeToOpen 的旧注释与一段「保险丝」孤儿注释
  （函数已移到 connect.ts）→ 已删除并改为指向单一实现。
- `xm2we.ts` 顶部「接口页 0xFF02」未说明它只是必要不充分条件 → 已补。

## 三、潜在 bug

### B-1 回退过滤器恒为空（功能性死代码）→ 本轮已修 ✅

- `main.ts` 精确 filter 落空后回退到 `{usagePage: 0xFF00}`，注释称
  「FF00–FFFF」。但 `DeviceFilter.usagePage` 是**精确匹配**，没有范围语义，
  所以只会匹配 usage page 恰好为 `0xFF00` 的集合 —— 现实中几乎不存在，
  回退列表实际上永远是空的。
- 修复：改为把 `0xFF00–0xFFFF` 逐页展开（256 页 × 2 个 VID），
  与注释语义一致；VID 仍限定，不会暴露指针/键盘页。

### B-2 OP1we 有线被标成 2.4G → 本轮已修 ✅

- `xm2we-ui.ts`：`wired = d.productId === WE_MOUSE_PID`，漏了 `0x1962`
  （OP1we 有线）。影响：连接状态文案、`readLink` 提示语义。
- 修复：两个鼠标 PID 都算有线。

### B-3 `rawReceive` 忽略 `DataView` 偏移 → 本轮已修 ✅

- `transport.ts`：`new Uint8Array(d.buffer)` 会取整块底层 buffer。
  规范允许实现返回子视图，此时会多读进无关字节，干扰长度/状态判定。
- 修复：`new Uint8Array(d.buffer, d.byteOffset, d.byteLength)`。

### B-4 同代跨型号导入不拦（已知残余风险）

- `main.ts` 只校验 `gen`，不校验 `device`/PID。同代布局一致，风险低，
  但 XM2w ↔ OP1w 的 CPI 上限/步进相同，仍可能导入不属于该型号的按键表。
- **建议**：导入时若 `j.device` 与 `S.mouseName` 不一致，二次确认。
  （`release-safety-audit.md` 已记录，未改。）

### B-5 XM2we 族的读数语义未经真机（已由总闸兜住）

- `readLink`/`readBattery` 用 `r[5]/r[6]/r[7]`，`readConfig` 用 `[3..4]`
  回显地址 —— 全部来自协议文档与离线仿真，**无真机背书**。
- 现状是安全的：`WE_WRITES_ENABLED = false`，整族只读；读错只会显示错，
  不会写坏。保持即可，不必改。

### B-6 `looksLikeBlob8k()` 的阈值是启发式（可接受）

- `levels ≤ 4 && active ≤ 3 && 10 ≤ cpi1 ≤ 30000` 用于区分「陈旧缓存帧」，
  偶发误判只会触发重试，不会写入。可接受。

## 四、架构审计

### 4.1 依赖方向（实测 import 图）

```text
                main.ts（启动 + DOM 绑定 + 各按钮）
   ┌───────────────┼──────────────────┬───────────────┐
 connect.ts     session.ts        xm2we-ui.ts      render/layout/presence
   │  │             │  │              │                 │
   │  └── xm2we-ui ─┘  │              └── xm2we.ts     └── state.ts
   │        │          │                   │
   │        └── transport.ts ──────────────┘
   │                │
   └── protocol.ts / blob.ts / verify.ts（纯逻辑，无 DOM）
```

- **无 import 环**（`xm2we.ts` 只依赖 `protocol.ts` 的纯表；`state.ts` 是叶子）。
- 分层清晰：纯协议（protocol/blob/verify）→ 传输（transport）→ 设备族
  （device-4k/8k/xm1、xm2we）→ 编排（session/connect/presence）→ UI
  （render/layout/xm2we-ui/main）。
- `err.ts` 单独成文件让协议层可在 Node 里 import —— 这个细节做得对。

### 4.2 优点

1. **单一状态源** `S` + 明确的「未连接即抛」契约（`dev()` / `blob()`），
   把最容易出错的前置条件收敛到两个函数。
2. **安全逻辑贴着发送点**：XM1 的白名单包在 `sendFeatureReport` 外层，
   调用方绕不过去 —— 这是从事故里总结出的正确做法。
3. **注释即证据链**：每处危险逻辑都写了「依据哪个函数/哪次差分」，
   可复核、可传承，比多数商业项目强。
4. **UI 白名单式布局**（`applyLayout`）从根上避免「切型号后残留卡片」。

### 4.3 问题与建议（按优先级）

1. **`main.ts` 577 行仍偏大**：DOM 绑定 + 导入导出 + 主题 + 预览钩子混在
   一起。建议拆 `boot.ts`（事件绑定）与 `io.ts`（导入/导出/诊断），
   `main.ts` 只留启动顺序。**收益中、风险低**，建议下轮做。
2. **闸门重复一份**（R-1）：抽 `gate.ts`，收益中、风险低。
3. **`verify.ts` 与 `device-8k.ts` 的校验函数高度相似**：
   `verifySensor8k` / `verifyPerf8k` 与 `verifySensor` / `verifyPerf`
   只差几个 gen 条件。可合并为带 `options` 的一份，减少「两处漏改」。
   **收益低**，可延后。
4. **`xm2we-ui.ts` 自带一份 `setConn()`**，与 `render.setConn` 重复；
   建议直接复用（无环：render 不 import xm2we-ui）。
5. **`S.queue` 的语义只在 4k 路径成立**（见 R-3）。架构上应把
   「报文串行化」作为传输层不变量，而不是某一族的使用习惯。
