# 发布前安全审计（2026-10-09）

> 问题：**假设已经发布，别人（尤其是那些我手上没有的型号）能"完全安全"地使用吗？**
>
> 结论：**不能给出"完全安全"的保证 —— 但可以给出按型号分级的、有依据的判断，
> 并且本次审计查出了 3 个真实缺陷，现已全部修复并钉进回归测试。**
>
> 一句硬话：对**你手上没有的型号**，本工具现在的行为是 **只读**；
> 唯一例外曾是你也没有的 WE 族（XM2we / OP1we），它此前竟然是**开放写入**的 —— 这是本次最严重的发现。

---

## 一、按型号的安全分级（审计后现状）

## 二、本次查出的三个缺陷（均已修复）

### ① WE 族写入是开着的，而且界面没有任何提示 —— 最严重

- `src/xm2we-ui.ts`：`btnWeApplyCpi` / `btnWeApplyPerf` 无条件可点，
  点下去就往 EEPROM 写 CPI / 回报率 / 去抖（`eeWrite`，命令 `0x07`）。
- 该族**从未接过失测真机**（29 项离线仿真 ≠ 真机）；
  有线 PID `0x1960` / `0x1962` 也没有任何真机实现背书
  （itchyfeetleech/OP1we-Control 只认接收器 `0x1961`，并注明有线 PID"未见真机"）。
- ⚠️ 关键点：**记录级回读校验（确实有）证明不了语义正确**。
  CPI 编码是 `(hw+1) × (mul ? 100 : 50)`，高位还打包进 M 字节；
  编码一旦理解错，写进去的就是另一个数量级的值，而回读**依然"一致"**。
- 修复：`src/xm2we.ts` 增加总闸 `WE_WRITES_ENABLED = false`（放在 `writeRecord` 里，
  离发送点最近）+ 按钮置灰 + 常驻只读警告（8 语言新增词条 `weUnverified`）。

### ② 8k 只读只靠界面置灰，协议层是放行的

- `guard4k()` 对 8k **不拦截**：判据 `(!S.gen && !S.eightK)` 在 8k 上为 false，
  且 8k 的 `S.unverified` 为 false。唯一屏障是 `render()` 里
  `canWrite = !!S.blob && !!S.gen && !S.unverified`（8k 的 `S.gen` 恒为 null）→ 按钮置灰。
- 但 `btnApplySensor.onclick` 是「先 `guard4k()` 再 `applySensor()`」，
  而 `applySensor()` 对 8k 直接 `return apply8k()` → **会真的发 `0x11` 整块写**。
- 这正是本项目自己写过的一条教训（`src/main.ts:476` 导入处的注释）：
  "单靠按钮 disabled 是不设防的"。8k 这条偏偏没补。
- 修复：`guard4k()` 开头显式拦截 `S.eightK`（含 `guard4k(false)` 的恢复出厂 / 配对 ——
  对有线 8k 发配对命令本身就没有意义）。

### ③ 导入配置不校验代际

- 原代码只校验 `b.length === 1024`。把 **v2 的配置导入 v1 设备**会按 v1 的编码写入：
  LOD（v1 整毫米 / v2 `round(mm×10)−7`）、按键区、LED 区布局都不同 → 字节错位。
- 修复：导入时比对 JSON 里的 `gen` 字段与当前设备 `gen`，不一致即拒绝
  （新增词条 `importGenMismatch`，8 语言）。旧版导出文件没有 `gen` 字段 → 不拦，保持兼容。

### ★ 未验证型号的写入口径：默认只读 + 点确认才放行

全禁和全开都不合适：全禁 → 远程志愿者（唯一有 8k / WE 设备的人）没法帮忙验证，
协议永远停在"未验证"；全开 → 别人一接上就能写没验证过的路径。所以是**四件套**：

1. **默认关**：`guard4k()`（8k）与 `writeRecord()`（WE）在闸门处拦住，不碰到设备。
2. **显式确认**：点写入按钮弹原生 `confirm()`，写明"未真机验证、可能不按预期生效、最坏要恢复出厂"。
   它是**同步**的 —— 没确认就一定走不到发送那一步。
3. **强制先备份**：确认后立刻自动导出一份当前配置（8k 导出 JSON，WE 导出 EEPROM dump），
   写坏了还有得救。
4. **只管本次连接**：`S.betaArmed` / `setWeWrites()` 在设备断开、复位、切后台时一律收回，
   **不写进 localStorage**，刷新页面即回到只读。

志愿者操作流程见 **[`docs/remote-beta-guide.md`](remote-beta-guide.md)**。

## 四、仍然存在的残余风险（这些消除不了，只能如实告知）

1. **写入过程中断电 / 拔接收器**：协议没有事务，理论上存在"写一半"的窗口。
   已做的缓解：写入后一律回读校验，不一致会逐项列出。
2. **恢复出厂不可撤销**：已有两道确认，但仍应在 README 里写明。
3. **XM1 只开放 23 个字节**：其余字节由回声闸门强制保持原值，这条是有证明的（可证明无损）。
4. **WebHID 只在 Chrome / Edge 可用**：页面已有环境检测横幅；Firefox / Safari 不会误写，只会连不上。
5. **误开指针/键盘集合会让鼠标动不了**：`isSafeToOpen()` 双重校验（open 前后各一次）已覆盖，
   其中**指针集合无条件拒绝**。键盘集合自 2026-10-20 起改为「与已知厂商配置集合
   （FF01:02 / FF02 / FFA1:00A5）共存时放行 + 警告」——Chrome 155 会把同一 USB 接口的
   顶层集合合并成一个 HIDDevice，有线 4k 鼠标必然带键盘集合，旧的「一律拒绝」等于
   禁掉全部有线配置；纯键盘设备（无厂商集合）仍在 `bNotVendor` 处被拦。
   指针集合的独占事故实测过一次（关掉页面即恢复）。
6. **同代不同型号之间互导配置**（如 XM2w ↔ OP1w，同 gen）：目前不拦。
   同族布局一致，风险低；若要收紧，可在导出 JSON 里再校验 `device` 字段。

## 五、发布建议

1. README 顶部用一段话写清：**"已真机验证的型号可读写；其余型号一律只读，界面会明确告知"**。
2. 保留 `WE_WRITES_ENABLED` 与 8k 闸门两个开关 —— 将来任一族拿到真机验证，
   改一个常量即可开放，不需要改结构。
3. 在求助帖/邮件里请志愿者**先在官方工具里截图备份配置**，
   并说明本项目历史上发生过一次"写坏配置"事故（XM1，2026-10-09）—— 诚实比包装更能换来志愿者。
