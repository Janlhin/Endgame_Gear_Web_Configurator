# 本项目 vs 官方配置工具：设置项对照与越界分析

> 2026-10-09 · 目的是回答一个问题：**我们的写入比官方工具更"激进"吗？
> 官方意味着安全放心，我们多写的部分是不是隐患？**
>
> 证据：官方工具 `re/upstream/*.exe`（六款，MFC，按 `MANIFEST.md` + `fetch.sh` 取回）
> 的**资源段字符串与 RTTI 类名**直接给出它有哪些设置页、每页有哪些控件；
> 对照本项目 `index.template.html` 与 `src/blob.ts` 的实际可写项。

## 一、结论（先说答案）

**我们没有比官方多写任何官方不写的字节。差距是"少"，不是"多"。**

| 维度 | 判断 | 依据 |
|---|---|---|
| 写入范围 | **我们更窄** | 4k 只发 `0x14`/`0x15` 两个 payload 帧；官方虽有整块 1024B 存储，我们没用 |
| 设置项数量 | **我们更少**（21 项 vs 官方 28 项） | 逐项对照见下表 |
| 字段编码 | **已按官方代码对齐** | CPI 下限/上限/步进来自反汇编（见 `re/PROTOCOL_NOTES.md`） |
| 是否写未知区 | **不写**（4k）／**整块写**（8k，已锁） | `buildSensorPayload` 只填已命名偏移，`p[0]` 显式透传原值 |
| 越界风险 | **无新增** | 缺项一律填 0 / 原值，语义见第三节 |

唯一"比官方多"的：**恢复出厂**（`0x13`）与**导入配置**两项危险操作，
两者都已有确认框 + 备份，且导入在 8k 上被硬闸门禁用。

## 二、逐项对照（以 XM2w 4k v2 官方工具为基准）

官方工具的四个页面（由 RTTI 类名确定：`CFixedCPI` / `CSensorDlg` / `CLedDlg` /
`CSupportDlg`）与资源段里的控件标签，加起来 28 个可调项。

| 官方设置项 | 本项目 | 写入方式 |

| CPI 1–4（X/Y） | ✅ | `0x14` p[8..27] |

| 当前激活档 | ✅ | `0x14` p[7] |

**21 项已开放 · 7 项未开放**。未开放的 7 项全部是"偏移未取证"或"已知但有意锁定"，
没有一项是"我们敢写但官方不写"。

## 三、为什么少写比多写更安全（关键论证）

官方工具的写入模型是**读整块 → 改内存副本 → 整块回写**。这意味着：
官方工具也会把**它不认识的字节原样带回去**（它自己也是读-改-写）。

本项目的模型不同：
- `buildSensorPayload()` 28 字节里，未命名的位置**只有 `p[0]`（blob[7]，语义未知）**，
  注释明写"勿清零——官方工具原样回写"，代码是 `S.stage.unk7 ?? 0`（从解析结果透传）；
- 其余每一字节都有名字、有官方依据、有 diff 实测记录（`re/PROTOCOL_NOTES.md`）；
- **不整块回写 1024B**，所以就算我们对某个字节理解错，也只错那一个字段，
  不会像整块写那样把未知区一起覆盖。

结论：**我们的写入面是官方写入面的真子集**（按字节算更小，按字段算更小）。
"官方意味着安全"这个直觉在**字段语义**上成立——我们只写官方也写的字段；
但在**写入粒度**上我们其实比官方更保守。

## 四、真正需要担心的不是"多写"，而是这三件

1. **字段语义错**（不是范围错）。风险最高的一项是 `angleTune`：
   位置在 `0x01`（本项目实测推断）还是 `0x70`（OpenMouse 记）**存在冲突，未定论**。
   目前按 v2 写 `0x14` p[5]，若推断有误，会写到 `0x01` 上——而 `0x01` 是有符号 24 位
   角度字段。**建议：真机确认前，把 angleTune 的 UI 降级为只读。**
2. **8k 整块写**。8k 是 `0x11` STORE 整块 1024B——**和官方一样的模型**，
   一旦某字节理解错，整块都受影响。所以 8k 默认只读 + 点确认才放行，这个闸门必须留着。
3. **写入中断电**。协议无事务。中断后设备可能半写，只能靠回读校验发现。
   这一点官方工具同样存在，不是我们独有的。

## 五、若决定"只留官方设置"——代价评估

把未开放的 7 项全部补齐（即"与官方对齐"）**不是收紧，反而是放开**：
新增 4 项灯效 + 左手模式 + 按键重映射 UI。每一项都需要先做偏移取证，
其中按键重映射涉及 `0x16` 双块写，风险等级高于现有任何一项。

**如果反过来担心"过度改写"，正确的收紧动作不是砍掉现有 21 项，而是：**
1. 把 `angleTune` 降级为只读（冲突未定的唯一一个已开放字段）；
2. 保留 8k 闸门；
3. 保留导入的代际校验与恢复出厂的确认框。

这三条能把"未验证导致写坏"的概率压到当前最低，而不需要牺牲任何官方已有的能力。
